# Обработка больших книг в EPUB (Large Books & Streaming Architecture)

Руководство по архитектуре разбиения глав, контролю байтового бюджета (300 KiB limit), потоковой оптимизации памяти и генерации электронных книг произвольного размера в `telegraph-publisher`.

---

## 1. Зачем нужно автоматическое разбиение глав

При сборке объемных книг (например, полных томов «Махабхараты», собраний комментариев, богословских трактатов и академических трудов) один Markdown-файл может содержать сотни тысяч строк текста. Без интеллектуального разбиения такой файл компилируется в **один гигантский XHTML-документ (10–50+ МБ)** с тысячами пунктов навигации.

Большинство аппаратных и программных читалок (e-readers):
- **Kindle (все поколения Paperwhite, Oasis, Basic)**,
- **Kobo (Clara, Libra, Sage)**,
- **PocketBook**,
- мобильные приложения Apple Books, Google Play Books, FBReader,

используют легковесные движки рендеринга (WebKit/Blink с жесткими ограничениями памяти процесса). При попытке открыть XHTML-файл размером более **~300 KiB**:
1. Читалка зависает («белый экран») на десятки секунд при инициализации DOM-дерева.
2. Перелистывание страниц и поиск по тексту происходят с задержками и рывками.
3. При нехватке оперативной памяти процесс читалки аварийно завершается (crash / reboot).
4. Оглавление с тысячами узлов в `toc.ncx` / `nav.xhtml` становится непригодным для навигации.

Для обеспечения плавной работы на всех устройствах в `telegraph-publisher` реализован алгоритм **автоматического потокового нарезания глав** с жестким контролем размера результирующего XHTML.

---

## 2. Байтовый бюджет и архитектура нарезки

### Точный лимит по умолчанию: 300 KiB (307 200 байт)

По умолчанию максимальный размер одного скомпилированного файла главы составляет **307 200 байт** (`DEFAULT_MAX_CHAPTER_BYTES = 300 * 1024`).

> [!IMPORTANT]
> Лимит рассчитывается по **точному размеру финального сериализованного XHTML в байтах UTF-8**, а не по исходному Markdown или количеству символов.

### Полный расчет бюджета документа

Каждый генерируемый XHTML-файл главы (`chapter-1.html`, `chapter-2.html`, ...) включает:
1. **XML-пролог и DOCTYPE**: `<?xml version="1.0" encoding="UTF-8"?>` и декларацию XHTML 1.1 (EPUB 2) или HTML5 (EPUB 3).
2. **Корневой тег и заголовки**: `<html xmlns="..." xml:lang="...">`, `<head>` с мета-тегом UTF-8, тегом `<title>` и ссылкой на `style.css`.
3. **Оболочку секции**: `<section epub:type="chapter" class="chapter">` или `<div class="chapter">`.
4. **Автоматический заголовок `<h1>`**: если исходная секция не начинается с `<h1>`, генератор синтезирует его с сохранением якорного `id`.
5. **Встроенную навигацию главы (In-text TOC / Blocks navbar)**: навигационную строку (например, `«К тексту: 1 · 20 · 40 · 60»`) в начале и конце части, если включен режим `--chapter-toc`.
6. **Полезную нагрузку (Atomic Units)**: параграфы, цитаты, стихи, списки, таблицы, блоки кода.
7. **Переписанные ссылки**: все внутренние ссылки `[ссылка](#якорь)` или `[глава](file.md#sec)` переписываются в точные межфайловые ссылки формата `href="chapter-X.html#target-id"`.
8. **Медиа-ссылки**: теги `<img src="images/img-1.png" alt="..."/>` с зарегистрированными в манифесте путями.

Генератор производит расчет размера документа **включая все открывающие и закрывающие теги обертки**.

## 3. Неделимые единицы (Atomic Units) и алгоритм разреза

### Принцип неделимости блоков

Для сохранения типографической и смысловой целостности текста генератор **никогда не разрезает контент по произвольным строкам**. Текст парсится в цепочку **атомарных блоков (`EpubAtomicUnit`)**:

| Тип блока | Семантика в EPUB | Правило неделимости |
|---|---|---|
| `heading` | Заголовки H1–H6 | Заголовок всегда сохраняет флаг `keepWithNext: true` (не отрывается от следующего за ним абзаца) |
| `paragraph` | Обычный абзац текста | Сохраняется целиком как один неделимый блок `<p>` |
| `code` | Блок кода (`<pre><code>`) | Неделим; синтаксические конструкции и отступы не разрываются |
| `table` | Таблица (`<table>`) | Неделима; структура строк `<tr>` и колонок `<td>` сохраняется |
| `list` | Список (`<ul>`, `<ol>`) | Неделим на уровне внешнего контейнера списка |
| `blockquote` | Блок-цитата (`<blockquote>`) | Неделим |
| `shloka` | Священные стихи / строфы | Строфы с мягкими переносами строк `<br/>` и номерами сохраняются атомарно |
| `html` | Необработанный HTML-блок | Сохраняется целиком в санированном виде |

### Монотонный алгоритм поиска точек разреза

Когда суммарный размер логической главы превышает бюджет (300 KiB):
1. **Поиск безопасных точек разреза (`safeCuts`)**: разрешен только между атомарными блоками, у которых предыдущий блок имеет `keepWithNext === false`.
2. **Иерархический приоритет**:
   - Приоритет отдается заголовкам более высокого уровня (H2, затем H3, H4...).
   - Если заголовков нет, разрез производится по границам параграфов.
3. **Префиксные суммы и бинарный поиск**:
   - Система строит префиксные суммы байтовых оценок блоков (`getUnitPrefixSums`).
   - Бинарным поиском находится максимальный суффикс блоков, помещающийся в текущую квоту.
   - Выполняется пробная сериализация для верификации границы с точностью до 1 байта.
4. **Гарантия завершаемости**: алгоритм строго монотонен — каждый шаг продвигает `currentStart` вперед минимум на один блок, исключая бесконечные циклы.

## 4. Политики обработки превышения размера (`--oversize-policy`)

Что происходит, если один неделимый блок (например, огромная таблица на 400 KiB или многостраничный блок кода) сам по себе превышает лимит 300 KiB?

Поведение регулируется флагом `--oversize-policy <warn|error>`:

### 1. `warn` (По умолчанию — безопасно для данных)
- Неделимый блок **сохраняется целиком** в отдельном документе главы. Текст **не обрезается** и не теряется.
- В отчет сборки (`EpubBuildReport`) записывается диагностическое предупреждение `W_OVERSIZE` с указанием точного размера в байтах, лимита и позиции в исходном коде.
- Процесс сборки завершается успешно с кодом возврата `0`.

### 2. `error` (Строгий контроль стандартов)
- При обнаружении любого блока, превышающего `maxChapterBytes`, сборка немедленно прерывается.
- Выбрасывается исключение `EpubBuildError` с кодом `E_OVERSIZE`.
- Выходной файл EPUB **не перезаписывается и не повреждается** (гарантия транзакционности).
- Процесс завершается с кодом возврата `1`.

### 3. Ошибка скелета документа (`E_WRAPPER_OVERSIZE`)
Если базовые теги HTML-обертки вместе с оглавлением главы превышают установленный размер (например, если пользователь установил абсурдно малый лимит вроде `--max-chapter-size 4096`), выбрасывается фатальная ошибка `E_WRAPPER_OVERSIZE`.

## 5. Потоковая оптимизация памяти (Stage B Memory Bounds)

Историческая реализация генераторов электронных книг накапливала весь контент и все AST-деревья в оперативной памяти Node.js/Bun, что приводило к `OutOfMemoryError` на файлах более 50–100 МБ.

В архитектуре `telegraph-publisher` реализован полностью потоковый конвейер:

```
[Markdown Source (64 KiB Chunks)]
               │
               ▼
   [EpubSourceScanner / BlockFramer]
               │
               ├──► [EpubSpoolStore (Disk Cache in tmp)]
               │        (Хранение сериализованных payloads)
               │
   [EpubLayoutPlanner (Pass 1: Sizing & Linking)]
               │
   [EpubXhtmlRenderer (Pass 2: Streaming Writers)]
               │
               ▼
   [EpubZipWriter (Two-pass Store/Deflate Streaming)]
               │
               ▼
   [Atomic Commit: package.epub -> book.epub]
```

### Ключевые механизмы экономии памяти:
1. **Чанковое чтение (`64 KiB chunks`)**: исходные Markdown-файлы читаются потоками фиксированного размера без загрузки всего файла в память.
2. **Дисковый Spool Store (`EpubSpoolStore`)**:
   - Распарсенные токены и полезная нагрузка блоков сразу сбрасываются во временный пул на диске (`EpubBuildSession.directory`).
   - В оперативной памяти хранятся только легковесные дескрипторы блоков (`id`, `range`, `kind`, `keepWithNext`).
   - Активным в памяти в любой момент времени является только один рабочий блок.
   - Пиковое потребление памяти ограничено $O(\max(\text{unit}) + \text{indexes})$, а не общим размером корпуса.
3. **Двухпроходный потоковый ZIP-архиватор (`EpubZipWriter`)**:
   - **Пас 1**: файлы глав записываются на диск; при формировании архива данные перекачиваются в ZIP-файл потоками без буферизации всего архива в RAM. Первым файлом всегда записывается несжатый `mimetype`.
   - **Пас 2**: в конец файла дописывается Central Directory.
   - Поддерживает стандартные ограничения ZIP32 (до 4 ГБ, до 65 535 файлов).
4. **Атомарный коммит и очистка**:
   - Сборка ведется в изолированном временном каталоге.
   - Перенос в целевой файл происходит только после успешной верификации через атомарный rename.
   - В случае ошибки или отмены (`AbortSignal`) все временные файлы гарантированно удаляются через `dispose()`.

### Результаты бенчмарков памяти (Peak RSS)
Тестирование на синтетических и реальных корпусах текстов на русском языке показало строго ограниченное масштабирование RSS:
- Корпус 20 MiB: пиковый RSS Bun процесса составляет **< 85 МБ**.
- Корпус 80 MiB: пиковый RSS стабилизируется в районе **< 110 МБ** (отсутствие линейной деградации памяти).

## 6. Управление через CLI флаги

### Основные флаги нарезки и диагностики

| Флаг | Тип / Значения | По умолчанию | Описание |
|---|---|---|---|
| `--max-chapter-size <size>` | Строка (`B`, `KiB`, `MiB`) | `300KiB` (307 200 B) | Максимальный размер XHTML-документа главы |
| `--no-auto-split` | Флаг (boolean) | `false` | Отключить автоматическую нарезку по размеру |
| `--split-at <1-6>` | Число от 1 до 6 | Не задан | Ручное разбиение по заголовкам указанного уровня |
| `--oversize-policy <mode>` | `warn` \| `error` | `warn` | Действие при неделимом блоке больше лимита |
| `--strict-links` | Флаг (boolean) | `false` | Считать неразрешенные внутренние ссылки ошибкой сборки |
| `--epub-report <path>` | Путь к файлу | Выключен | Сохранить детальный JSON-отчет о сборке |
| `--epub-dry-run` | Флаг (boolean) | `false` | Выполнить анализ и нарезку без записи файла EPUB |
| `--toc-depth <n>` | Число от 1 до 6 | Все заголовки | Глубина оглавления читалки (`toc.ncx` / `nav.xhtml`) |
| `--chapter-toc <mode>` | `none` \| `blocks` \| `full` \| `auto` | `auto` | Режим оглавления в тексте главы |
| `--book-toc <pos>` | `start` \| `end` | Выключен | Отдельная страница полного оглавления книги |

> [!CAUTION]
> Флаги `--max-chapter-size` и `--no-auto-split` являются **взаимоисключающими**. Их одновременное указание приведет к ошибке `E_OPTION` с кодом возврата `2`.

## 7. Практические примеры использования

### Пример 1. Стандартная сборка большой книги с дефолтным лимитом 300 KiB

```bash
telegraph-publisher epub \
  -f mahabharata-full.md \
  -a "Вьясадева" \
  -t "Махабхарата" \
  -o mahabharata.epub
```
*Книга будет автоматически нарезана на главы размером не более 307 200 байт каждая. Ссылки между шлоками и главами сохранятся.*

### Пример 2. Сохранение ручного разбиения по главам плюс нарезка крупных глав

```bash
telegraph-publisher epub \
  -f volume1.md volume2.md \
  -a "Автор" \
  -t "Собрание сочинений" \
  --split-at 2 \
  --max-chapter-size 250KiB \
  --toc-depth 2 \
  -o library.epub
```
*Разделы уровня H2 выделяются в отдельные части; если какой-либо раздел H2 превышает 250 KiB, он автоматически делится на подчасти.*

### Пример 3. Предварительный анализ без генерации (Dry-Run) и экспорт отчета

```bash
telegraph-publisher epub \
  -f huge-encyclopedia.md \
  -a "Редакция" \
  --epub-dry-run \
  --epub-report build/report.json
```
*Команда завершается быстро, не создает архив `.epub`, но генерирует подробный `report.json` со списком всех документов, их точными размерами и диагностиками.*

### Пример 4. Строгий режим для издательского пайплайна

```bash
telegraph-publisher epub \
  -f treatise.md \
  -a "Философ" \
  --oversize-policy error \
  --strict-links \
  --max-chapter-size 300KiB \
  -o treatise.epub
```
*Сборка прервется с ошибкой, если в документе есть сломанные локальные ссылки или блоки текста более 300 KiB.*

## 8. Валидация пакета и проверка целостности

### Автономный верификатор `scripts/verify-epub-package.py`

В репозиторий включен строгий валидатор пакетов EPUB на чистом Python 3 (без сторонних зависимостей):

```bash
python3 scripts/verify-epub-package.py path/to/book.epub --max-xhtml-bytes 307200 --report report.json
```

**Что проверяет верификатор:**
1. **Целостность ZIP**: выполнение `zipfile.testzip()` без поврежденных контрольных сумм CRC-32.
2. **Стандарт `mimetype`**: первый элемент архива строго несжат (STORED, 0 байт сжатия), имеет имя `mimetype` и содержимое `application/epub+zip` без extra fields.
3. **POSIX-сортировка**: остальные элементы архива отсортированы в лексикографическом порядке.
4. **Структура контейнера**: корректный `META-INF/container.xml`, указывающий на корневой файл пакета (`OEBPS/content.opf`).
5. **Валидность XML и XHTML**: разбор каждого файла манифеста и spine через XML-парсер.
6. **Контроль размера файлов**: байтовый размер каждого файла spine XHTML не превышает `--max-xhtml-bytes` (если не передан `--allow-oversized`).
7. **Целостность внутренних ссылок**: все якоря вида `href="chapter-2.html#verse-45"` проверяются на реальное присутствие элемента с `id="verse-45"` в целевом документе.
8. **Наличие ресурсов**: все упомянутые изображения и таблицы стилей физически присутствуют в архиве.

### Совместимость с EPUBCheck

Пакеты, генерируемые `telegraph-publisher`, разрабатываются с учетом спецификаций **IDPF / W3C EPUB 3.3 и EPUB 2.0.1**.

При наличии установленного официального валидатора `epubcheck` (Java JAR или CLI):
```bash
epubcheck book.epub
```
Пакет проходит валидацию структуры, манифеста и навигационных документов `nav.xhtml` и `toc.ncx`.
